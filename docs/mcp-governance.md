# MCP governance through the gateway

The Terminal Ops MCP server is not called directly any more. Every consumer (Foundry agents, the CLI agent, smoke tests) goes through APIM, which authenticates the caller, decides which tools its team may call, rate-limits, meters and logs the calls, and is the only party holding the key of the MCP backend.

```
Foundry agent / CLI / any MCP client
   |  https://<apim>/mcp/<team>        header api-key = team key   (or Authorization: Bearer <Entra, Team.* role>)
   v
APIM  native MCP API  mcp-<team>   (infra/policies/mcp-api-policy.xml)
   1 authenticate        subscription key of product mcp-<team>  OR  validate-azure-ad-token (Team.Ops/IT/CS)
   2 team == path team   else 403
   3 inspect JSON-RPC    tools/call -> params.name must be in named value mcp-tools-<team>, else JSON-RPC error
   4 rate-limit-by-key   mcp-rate-limit-per-min calls/min per team+caller (tools/call), 429 beyond
   5 emit-metric         McpToolCalls {Team, Tool, Result=allowed|blocked, ClientApp}
   6 set x-mcp-key       named value mcp-backend-key (secret); gateway key / Entra token are NOT forwarded
   v
Container App ca-portops-mcp   /<team>/mcp   (tools/list is already scoped server-side)  - rejects calls without x-mcp-key (401)
```

## Layers (defense in depth)
| Layer | Where | What it enforces |
|---|---|---|
| Agent | Foundry `MCPTool.allowed_tools`, `require_approval` | Tools the model may see / whether a human approves each call |
| Gateway identity | APIM product `mcp-ops|it|cs` key, or Entra token with `Team.*` role | Who is calling; the team must match the path (`/mcp/ops` with the `it` key = 403) |
| Gateway tool allow-list | Policy + named values `mcp-tools-<team>` | `tools/call` for a tool outside the team list is refused, even if the backend would serve it |
| Gateway limits + telemetry | `rate-limit-by-key`, `emit-metric McpToolCalls`, diagnostics (no bodies) | Abuse limit, per team/tool/result visibility |
| MCP server | `/<team>/mcp` endpoints + `MCP_API_KEY` (`x-mcp-key`) | Only the scoped tools exist; direct calls without the APIM-held key get 401 |

## Design choices
- **Native APIM MCP API** (`type: mcp`, API version `2024-06-01-preview`, works on BasicV2), one per team, each with an APIM backend `https://<container-app>/<team>/mcp`. Bicep types do not know `backendId`/`mcpProperties` yet (BCP037 suppressed) but ARM accepts them. The policy can read the **request** body (JSON-RPC) but never touches responses (they stream). Fallback if native type is unavailable: HTTP passthrough API with wildcard POST/GET/DELETE operations and the same policy.
- **Denied tool call = HTTP 200 + JSON-RPC error `-32001`** (`Tool 'x' is not permitted for team 'y' (gateway tool allow-list)`). MCP clients surface it as a tool error the agent can react to, instead of a transport failure that aborts the session. Response header `x-portops-mcp-result: blocked` and metric `Result=blocked` record it. Auth failures stay HTTP 401/403.
- **Foundry authentication**: `MCPTool.headers` is *not persisted* in agent definitions (verified: stored tool has no headers), so each project has a **CustomKeys connection `mcp-gateway-<team>`** (key name `api-key`, value = team key) and the tool uses `project_connection_id`. Created by `scripts/deploy-mcp.ps1`. `allowed_tools`/`require_approval` stay on the tool.
- **Backend key** is generated by `deploy-mcp.ps1`, stored only as Container App secret `mcp-backend-key` (env `MCP_API_KEY=secretref:`) and APIM secret named value `mcp-backend-key`; re-runs reuse it. The APIM MCP layer is deployed by that script (`infra/modules/apim-mcp.bicep`), not by `main.bicep`, so a main redeploy never overwrites the secret. If you rotate it, re-run the script.
- Every MCP API is in each `mcp-<team>` product; the policy (not product membership) decides team == path so a wrong-team caller gets an explicit 403 rather than a generic 401.

## Change a team's allowed tools (portal, no deployment)
APIM > **Named values** > `mcp-tools-ops` (or `-it`, `-cs`) > edit the comma-separated list > Save. Takes effect within seconds to a minute (named-value cache). Same for `mcp-rate-limit-per-min`. To also hide a tool from `tools/list`, change `mcp/departments.py` (server-side scope) and the Foundry `allowed_tools`.

## Demo
```powershell
cd demo
python mcp_governance_demo.py     # (a) allowed tool OK  (b) cs -> get_berth_plan blocked  (c) it key on /mcp/ops 403  (d) direct container call 401  (e) KQL
python run_all_smoke.py           # includes the four MCP governance checks (--skip-mcp-gov to skip)
```
KQL (metric appears within a few minutes):
```kusto
AppMetrics
| where Name == "McpToolCalls"
| extend Team = tostring(Properties.Team), Tool = tostring(Properties.Tool), Result = tostring(Properties.Result)
| summarize Calls = sum(Sum) by Team, Tool, Result
| order by Team asc, Tool asc
```
Gateway log view: `ApiManagementGatewayLogs | where ApiId startswith "mcp-" | summarize count() by ApiId, ResponseCode` (request/response bodies are not logged).

## Talking point (not built): user context vs managed identity for SharePoint/Confluence MCP
Our MCP tools hold no user data, so the gateway authenticates *the caller/team*. A SharePoint or Confluence MCP is different: the answer depends on **who asks**. With a shared managed identity / service account the MCP sees everything that identity can see, so every user gets the same (over-broad) data, or "unauthorized" for everybody. The target pattern is **identity passthrough / On-Behalf-Of**: the user's Entra token (audience = the gateway API) is validated by APIM (`validate-azure-ad-token`, as in `entra-api-policy.xml`), exchanged via OBO for a token to the downstream (Graph / SharePoint) or sent to the MCP server so permissions are trimmed to the user; APIM keeps the audit trail (`ClientApp`/user dimension). Foundry side: MCP connection with OAuth identity passthrough instead of a shared key.
